# Wasi — Project Context (auto-loaded by Claude Code)

## What this is

Wasi is a WhatsApp Business CRM: a client-facing app (chat inbox, contacts, campaigns, templates, automation), an internal admin panel for onboarding/operating client accounts, and a public marketing/signup site — all backed by a real Express + Postgres backend on Meta's WhatsApp Cloud API. A Hub API (`/api/v1/*`) and an MCP server let third-party apps and AI assistants send messages and read data through a client's own account.

## Architecture summary

Plain CommonJS Node, no build step, no TypeScript. Three static-HTML/vanilla-JS surfaces sharing one Express backend (`server/`):
- **Root CRM app** (`index.html`/`index.css`/`app.js`) — the logged-in client app.
- **`admin/`** — the internal ops console (separate login, `requireAdminAuth`).
- **`marketing/`** — public landing page + signup wizard, no auth.
- **`mcp-server/`** — standalone npm package wrapping the Hub API as MCP tools for AI clients (local/stdio transport only).

See `server/README.md` for the API surface and background workers, `DEPLOY.md` for production deploy, `crm-integration-guide.md` for the Hub API's own docs (distinct audience from this file — see the Update mechanism section below), `wasi-master-plan.md` for the long-range feature roadmap this table tracks against.

- **The New Campaign modal has no UI for per-template parameter mappings** — found live during this session's own UI verification: launching a campaign against ANY template with `{{named}}` parameters fails server-side ("This template has parameters with no value source") because the modal has never sent a `paramMappings` field, predating this session entirely (the Hub API's `POST /api/broadcasts` and this session's `broadcastPacing.test.js` both work fine because they set `paramMappings` directly via the API, bypassing this UI gap). Today a client can only launch a UI-created campaign against a template with a static body (no variables) — a real, pre-existing limitation, not introduced or fixed this session.
- **`broadcastRecipientsRepo.claimBatch` had a real, silent, PG17-specific bug, fixed 2026-08-28 — precise finding, not a vague "known anti-pattern" claim.** The original SQL (`UPDATE broadcast_recipients SET status='sending' WHERE id IN (SELECT ... LIMIT $2 FOR UPDATE SKIP LOCKED) RETURNING *`) does NOT reliably respect its own `LIMIT` once wrapped in the outer `UPDATE` — but this needed real cross-checking to pin down: this project's independent Auditor first could NOT reproduce it (local Postgres 16 via Docker, single-call and 10-way-concurrent, both correct). Re-verified directly against this app's actual database — **Supabase-managed Postgres 17.6** (confirmed via `select version()`) — with 3 repeated trials of each SQL form on identical data: the old form claimed all 5 pending rows for `limit=1` in every trial; the CTE replacement claimed exactly 1 in every trial. Deterministic and reproducible on the real deployment target, not a flaky artifact — a genuine PG16-vs-17(-or-pooler) behavior difference for this exact query shape. Invisible before this session because the constant `BATCH_SIZE=25` rarely bound against real pending counts in practice; this session's finer-grained `pacing_config` (sometimes `limit=1`) is what made the symptom observable. Fixed with the standard CTE form (`WITH claimed AS (SELECT ... LIMIT $2 FOR UPDATE SKIP LOCKED) UPDATE ... FROM claimed WHERE ... RETURNING ...`), which is the textbook-correct SKIP-LOCKED-queue pattern regardless of this specific version finding.
- **`broadcastRunner.js` hardening from the independent Phase 3 audit, fixed 2026-08-28**: (1) `effectiveBatchSize` now guards with `Number.isFinite` — a non-numeric `pacing_config.messages_per_minute` (schema-validated at creation, but nothing enforced that at the DB layer, unlike `tag_id`/`contact_list_id`'s mutual exclusivity which has both a schema AND a DB CHECK) produced `NaN`, which Postgres rejects as a `LIMIT` parameter; that exception propagated out of `processBroadcast` uncaught into `tick()`'s single try/catch around its whole loop, meaning one broadcast with a bad `pacing_config` could abort every OTHER client's active broadcast for that tick, indefinitely (the bad broadcast stays `'Sending'` and gets re-selected every 5s). (2) `tick()`'s per-broadcast loop now has its own try/catch per iteration, not one around the whole loop — general robustness, not just for the `NaN` case, so any future error processing one client's broadcast can't starve everyone else's.
- **`contactListsRepo.addMembersFromRows` race condition, fixed 2026-08-28**: the original SELECT-then-INSERT pattern for deduping a CSV row's phone against existing contacts was a real TOCTOU race — two concurrent imports creating the same new phone could both pass the SELECT, then the second INSERT would hit `contacts`' real `unique(client_id, phone)` constraint uncaught, aborting the entire import with a bare 409 and no imported/errors report, even though every row before the collision had already committed. Fixed with a single atomic `INSERT ... ON CONFLICT (client_id, phone) DO UPDATE` (the DO UPDATE clause is a no-op, purely so `RETURNING` fires on conflict — matches `contactsRepo.upsertByPhone`'s established "don't overwrite an existing name" precedent, doesn't overwrite anything).
- **Template edit (`PUT /api/templates/:id`) can't change a media header** — its schema (`messageTemplateUpdateSchema`) only accepts `header.type` of `NONE`/`TEXT`; a template that already HAS an `IMAGE`/`VIDEO`/`DOCUMENT` header can't be edited at all through this route (the whole form is locked in the UI when that's the case), and a `NONE`/`TEXT` template can't be switched TO a media header via edit either. Reason: adding/changing a media header needs the same Resumable-Upload-handle dance `POST /` does at creation time (`createUploadSession`/`uploadFileBytes`), which this route doesn't replicate — deliberately out of scope for this pass, not forgotten. Delete + recreate (`DELETE /:id` then `POST /`) is still the only path for that case, same as for an orphaned row. None of Fortune Innovatives' 17 templates use a media header, so this didn't block the audit that prompted building edit in the first place.
- **Template edit resubmits the ENTIRE template for re-review, not just the new field** — this is Meta's own behavior (confirmed via the Edit Message Templates API), not a choice this app made: editing an approved template's buttons puts the WHOLE template back into `pending` review, even though the old approved content keeps sending in the meantime. `messageTemplatesRepo.updateContent` reflects this by resetting `status` to `'pending'` on every edit, unconditionally.
- **No editable UI for Authentication templates' OTP button type** — `messageTemplateUpdateSchema` accepts `otpButtonType` (matching create), but the Edit modal's Authentication fields only ever expose expiration/disclaimer (same as Create's) — `otpButtonType` is hardcoded to `'COPY_CODE'` client-side either way, since `ONE_TAP` was never built (see `metaClient.js`'s `buildAuthenticationPayload` comment).
- **Zapier integration (2026-08-28) scope decisions, not oversights**: (1) the "Send WhatsApp Message" action supports text + template message types only — interactive buttons/lists need dynamic field mapping that doesn't fit Zapier's static form-field UI well, deferred. (2) The "New WhatsApp Message Received" trigger has no polling/"load sample data" fallback — Wasi has no endpoint to list recent inbound messages on demand, so a user testing the trigger during Zap setup must send a real WhatsApp message first. (3) `zapier_subscriptions.event` is CHECK-constrained to `'message.received'` only, matching the one trigger actually built — widen the constraint (migration) and `zapierSubscribeSchema` (`validate.js`) together if a second trigger (e.g. delivery-status) ships later, same discipline as migration `032_widen_forward_events.js`.
- **Zapier integration: 4 real defects found by the independent Auditor/QA pass, all fixed same session (2026-08-28), plus one deliberately partial fix left honest.** (1) Revoking or soft-deleting an API key (`routes/apiKeys.js`) previously left its Zapier subscription(s) silently alive forever — `apiKeysRepo.revoke`/`softDelete` only ever set `revoked_at`/`deleted_at` columns, never a real SQL `DELETE`, so migration 040's `api_key_id` `ON DELETE CASCADE` never fired; contradicted both that migration's own comment and the client-facing revoke-confirm dialog's explicit promise. Fixed: both handlers now explicitly call `zapierSubscriptionsRepo.removeByApiKeyId`. (2) The HMAC secret `apiV1Subscriptions.js` generates and returns — stated purpose "for the Zapier app to store... and verify the x-wasi-signature-256 header" — was never actually checked anywhere; `zapier-app/triggers/newMessageReceived.js`'s `perform()` just returned the payload unverified, meaning anyone who discovered a client's live Zapier catch-hook URL could inject fabricated "customer messaged you" events. Fixed: migration 041 adds `unique(client_id, target_url, event)`, `zapierSubscriptionsRepo.create` upserts (`ON CONFLICT ... DO UPDATE`), preserving the original secret across a re-subscribe. (4) `POST /api/api-keys` (client self-serve key creation, this same session) had no rate limit at all — the one Hub-API-adjacent route with none. The identical unaddressed gap already exists on `wabas.forward_to_url`/`client_webhooks.callback_url` (both bare `z.string().url()`, no host check) — inherited by the new schema, not introduced by it. A real follow-up: an env-gated bypass (mirroring `ALLOW_SHARED_PRODUCTION_DB`'s shape) so full private-range blocking can ship across all three schemas without breaking legitimate local test targets.

## Conventions this codebase follows

- Plain CommonJS, no TypeScript, no bundler on any of the three front-end surfaces.
- Backend tests: `node --test` (built-in runner), no jest/mocha. Outbound Meta calls are faked by stubbing `global.fetch` for `graph.facebook.com` URLs only — never the app's own local-server fetches.
- **Local `DATABASE_URL` is the same shared Supabase instance as production** — there is no separate dev database. `server/src/utils/dbSafety.js` refuses any DB-touching script/test by default; set `ALLOW_SHARED_PRODUCTION_DB=yes-i-understand-the-risk` for that one invocation (never in `.env`) when a real DB round-trip is genuinely needed. Use a clearly-prefixed disposable test client (see `server/test/apiV1.test.js`'s `before()`/`after()`), never the demo/production accounts, for anything that writes.
- Migrations via `node-pg-migrate` (`npm run db:migrate` in `server/`), never raw SQL against the live schema.
- Two responsive breakpoints, defined once in `breakpoints.css` as CSS custom properties (reference only — `@media` conditions can't consume a custom property, so every actual media query hardcodes the literal px value): 900px tablet, 640px mobile.
- Never run `server/src/index.js` directly for anything but the real deployed server — use `createApp()` (from `server/src/app.js`) directly, listening on an ephemeral port, for any local/test/verification use.
- Secret/credential leak discipline: this project has shipped two real leak bugs to production (`forward_secret` via a hand-rolled destructure; `key_hash` via `returning *` + spread) — both fixed by (a) reusing one shared masking/shaping helper across every route returning the same shape rather than hand-rolling per-route, (b) auditing every sibling route returning the same table/shape while in there, (c) adding regression test coverage in the same change. Apply this discipline to any new response shape.
- **Hub API v1 (`/api/v1/*`) error responses**: always `{ "error": { "code": "...", "message": "...", ...optional extra fields } }` — never a bare string or a route-specific ad-hoc shape. Use `server/src/utils/apiError.js`'s `sendApiError()` for a known failure in a route handler; anything thrown (Zod, Postgres constraint violation, uncaught) is normalized by `server/src/middleware/apiV1ErrorHandler.js`. This shape is scoped to `/api/v1/*` only — admin/marketing/client-CRM routes keep the pre-existing `{ error: "string" }` shape via `server/src/middleware/errorHandler.js`, unchanged. Every `/api/v1/*` response also carries live `X-RateLimit-Limit`/`X-RateLimit-Remaining`/`X-RateLimit-Reset` headers (`rateLimit.js`'s `apiLimiter`, `legacyHeaders: true`).
- Feature-inventory status column uses three states — *Not started / In progress / Complete + verified* (*Live* is used interchangeably with *Complete + verified* for pre-existing shipped capability). Don't mark something without real test evidence.
- **This shared database has REAL, LIVE background workers polling it right now** (`broadcastRunner`/`forwardRunner`/`flowRunner`/`alertRunner`, if the real production server is up — it normally is). This is a stronger warning than "don't run `src/index.js` locally": even using `createApp()` correctly (never starting these runners yourself), a test that creates a row matching what a LIVE runner elsewhere polls for (e.g. a `broadcasts` row with `status='Sending'`) can get raced and partially processed by that live instance — confirmed for real during Phase 3 testing (a test broadcast in `'Sending'` status was picked up and its recipients partially processed by something outside the test process, using production's own `SERVER_SECRET` to decrypt a token this test had encrypted under its own local key, producing a confusing GCM auth-tag failure that looked exactly like an application bug until traced). **The fix**: give a test row a status/timing a live poller's own query genuinely excludes (e.g. `broadcasts.status='Scheduled'` with a future `scheduled_date` — invisible to both `listActive()` and `listDueScheduled()`), then invoke the runner's processing function directly (`broadcastRunner.processBroadcast(row)`) rather than `.tick()` (which scans and would touch every client's active work on this shared DB, not just yours). Before writing any test that creates a row for ANY background-runner-owned table, check what status/query that runner actually polls for and deliberately avoid it.
- **New reference-content tables** (e.g. `template_library`): seed via an idempotent script under `server/src/db/` (`seedTemplateLibrary.js`'s pattern: upsert by a real unique natural key, never delete-then-reinsert — a client-generated child row like `template_library_usage` would otherwise be orphaned across re-seeds even with `ON DELETE CASCADE`, since a fresh insert gets a new id). Validate content against the SAME real functions the actual submission path uses (`templateParams.js`'s `validateTemplateText`/`validateHeaderText`) before it ever reaches a client, not hand-eyeballed — see `templateLibraryValidation.js`. A migration adding a table a real client will write real rows into should give its `down()` a live-row check before dropping (same pattern as migration `032_widen_forward_events.js`'s down()), not a bare `DROP TABLE`.

## Update mechanism (how this file stays current)

1. Every build prompt for a new feature ends with an explicit "update CLAUDE.md" instruction, and a build isn't complete without it — same bar as a build without tests.
2. Keep this file, `crm-integration-guide.md`, and the in-app API Guide (`admin/index.html`'s "API Guide" view) in sync but distinct: this file is for Claude Code/internal developers (architecture, conventions, status); the other two are for external developers integrating (endpoints, auth, examples). They overlap in content but serve different readers — don't merge them.
3. Update the feature-inventory table's status honestly, using the three states above — never mark something "Complete + verified" or "Live" without real test evidence.
4. If two sessions touch this file concurrently (this project's local DB is shared, and more than one Claude Code session may be active against the same working tree at once — confirmed to happen in practice), **merge, don't overwrite**: read the currently-committed version first, keep its content intact, and add/update only the rows and sections your own change actually affects.
