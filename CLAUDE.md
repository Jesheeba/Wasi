# Wasi — Project Context (auto-loaded by Claude Code)

## What this is

Wasi is a WhatsApp Business CRM: a client-facing app (chat inbox, contacts, campaigns, templates, automation), an internal admin panel for onboarding/operating client accounts, and a public marketing/signup site — all backed by a real Express + Postgres backend on Meta's WhatsApp Cloud API. A Hub API (`/api/v1/*`) and an MCP server let third-party apps and AI assistants send messages and read data through a client's own account.

## Architecture summary

Plain CommonJS Node, no build step, no TypeScript. Three static-HTML/vanilla-JS surfaces sharing one Express backend (`server/`):
- **Root CRM app** (`index.html`/`index.css`/`app.js`) — the logged-in client app.
- **`admin/`** — the internal ops console (separate login, `requireAdminAuth`).
- **`marketing/`** — public landing page + signup wizard, no auth.
- **`mcp-server/`** — standalone npm package wrapping the Hub API as MCP tools for AI clients (local/stdio transport only).

See `server/README.md` for the API surface and background workers, `DEPLOY.md` for production deploy, `crm-integration-guide.md` for the Hub API's own docs (distinct audience from this file — see the Update mechanism section below), `wasi-master-plan.md` for the long-range feature roadmap this table tracks against.

## Known gaps / deliberately deferred

- **Root CRM app: `GET /api/auth/me` (the session-check called on every page load/reload) shared `authLimiter`'s strict 20-req/15-min bucket with `/login`/`/register` — fixed 2026-09-01, found live on the production site.** Reported as "if I refresh the page repeatedly, the system logs me out" — the resume-check IIFE's `authFetch('/api/auth/me')` call would start returning 429 after routine, completely normal repeated reloading (very plausible during a work session, or while troubleshooting the earlier session-resume fixes), and since neither `showResumeConfirm` nor `enterApp` is ever called on a thrown error, the user was left staring at a bare, unexplained login screen — no toast, no error, looking exactly like a logout, for up to 15 minutes. Confirmed live: 25 real `GET /api/auth/me` calls with a valid token, only 20 would have succeeded under the old shared limiter. **Fix**: `authLimiter` is no longer applied blanket to the whole `/api/auth` router (`server/src/app.js`) — it's now applied per-route in `routes/auth.js`, kept on the genuinely credential-guessable endpoints (`/register`, `/login`, `/forgot-password`, `/reset-password`, `/verify-email`), while `/me` and `/verify-email/request` (both already gated behind `requireClientAuth` — a valid JWT, not brute-forceable the way a password is) get a new, much more generous `sessionCheckLimiter` (60/min vs. 20/15min — `server/src/middleware/rateLimit.js`). Verified live: 25/25 `/me` calls now succeed; `/login` brute-force protection confirmed still fully intact (still 429s after repeated bad attempts); `server/test/api.test.js`'s existing 13 tests all still pass.
- **Live "flag while typing" template validation, added 2026-09-01 — the Create/Edit Template modal previously only checked one rule (malformed placeholder names) as the user typed; every other real rejection reason (numbered/mixed parameters, a variable at the very start/end, the words-to-parameters ratio, missing sample values) only ever surfaced after a failed submit.** Fixed by making `server/src/utils/templateParams.js` genuinely shared instead of hand-duplicated: it was already pure, dependency-free JS (confirmed before changing anything), so it now dual-exports for Node `require()` and a plain browser global (`if (typeof module...) {...} else if (typeof window...) {...}`), served as-is via a new static route (`GET /templateParams.js`, `server/src/app.js`) and loaded in `index.html` before `app.js` — no build step needed, matching this repo's existing `embeddedSignup.js` static-file precedent. `app.js`'s Create/Edit modal now calls `window.templateParams.validateTemplateText`/`validateHeaderText` directly — the EXACT same functions `routes/templates.js`'s `validateStandardTemplateFields` runs at submit time — plus a client-side port of that function's one extra rule (missing sample values), wired to the body/header `input` listeners, the sample-value inputs, and category/header-type changes. ## Conventions this codebase follows

- Plain CommonJS, no TypeScript, no bundler on any of the three front-end surfaces.
- Backend tests: `node --test` (built-in runner), no jest/mocha. Outbound Meta calls are faked by stubbing `global.fetch` for `graph.facebook.com` URLs only — never the app's own local-server fetches. **`npm test` (`server/package.json`) always passes `--test-concurrency=1`** — node's default concurrent-file execution was found (2026-09-03) to race multiple test-file processes against this shared local/prod database, causing real, reproducible failures in more than one file pair (two Playwright files binding the same fixed port 4000; two files both triggering real admin refreshes against the same `meta_template_library_cache` table — see this file's Known Gaps for both). Forcing concurrency to 1 serializes every file (one process fully exits before the next starts), which resolved every instance of this found so far and lets the whole suite run as a single `npm test` invocation instead of hand-split batches. If a new test file introduces a similar shared-resource conflict, prefer designing it to avoid the collision (a unique port, a disposable/isolated table row) over reaching for higher concurrency again.
- **Local `DATABASE_URL` is the same shared Supabase instance as production** — there is no separate dev database. `server/src/utils/dbSafety.js` refuses any DB-touching script/test by default; set `ALLOW_SHARED_PRODUCTION_DB=yes-i-understand-the-risk` for that one invocation (never in `.env`) when a real DB round-trip is genuinely needed. Use a clearly-prefixed disposable test client (see `server/test/apiV1.test.js`'s `before()`/`after()`), never the demo/production accounts, for anything that writes.
- Migrations via `node-pg-migrate` (`npm run db:migrate` in `server/`), never raw SQL against the live schema.
- Two responsive breakpoints, defined once in `breakpoints.css` as CSS custom properties (reference only — `@media` conditions can't consume a custom property, so every actual media query hardcodes the literal px value): 900px tablet, 640px mobile.
- Never run `server/src/index.js` directly for anything but the real deployed server — use `createApp()` (from `server/src/app.js`) directly, listening on an ephemeral port, for any local/test/verification use.
- Secret/credential leak discipline: this project has shipped two real leak bugs to production (`forward_secret` via a hand-rolled destructure; `key_hash` via `returning *` + spread) — both fixed by (a) reusing one shared masking/shaping helper across every route returning the same shape rather than hand-rolling per-route, (b) auditing every sibling route returning the same table/shape while in there, (c) adding regression test coverage in the same change. Apply this discipline to any new response shape.
- **Hub API v1 (`/api/v1/*`) error responses**: always `{ "error": { "code": "...", "message": "...", ...optional extra fields } }` — never a bare string or a route-specific ad-hoc shape. Use `server/src/utils/apiError.js`'s `sendApiError()` for a known failure in a route handler; anything thrown (Zod, Postgres constraint violation, uncaught) is normalized by `server/src/middleware/apiV1ErrorHandler.js`. This shape is scoped to `/api/v1/*` only — admin/marketing/client-CRM routes keep the pre-existing `{ error: "string" }` shape via `server/src/middleware/errorHandler.js`, unchanged. Every `/api/v1/*` response also carries live `X-RateLimit-Limit`/`X-RateLimit-Remaining`/`X-RateLimit-Reset` headers (`rateLimit.js`'s `apiLimiter`, `legacyHeaders: true`).
- Feature-inventory status column uses three states — *Not started / In progress / Complete + verified* (*Live* is used interchangeably with *Complete + verified* for pre-existing shipped capability). Don't mark something without real test evidence.
- **This shared database has REAL, LIVE background workers polling it right now** (`broadcastRunner`/`forwardRunner`/`flowRunner`/`alertRunner`, if the real production server is up — it normally is). This is a stronger warning than "don't run `src/index.js` locally": even using `createApp()` correctly (never starting these runners yourself), a test that creates a row matching what a LIVE runner elsewhere polls for (e.g. a `broadcasts` row with `status='Sending'`) can get raced and partially processed by that live instance — confirmed for real during Phase 3 testing (a test broadcast in `'Sending'` status was picked up and its recipients partially processed by something outside the test process, using production's own `SERVER_SECRET` to decrypt a token this test had encrypted under its own local key, producing a confusing GCM auth-tag failure that looked exactly like an application bug until traced). **The fix**: give a test row a status/timing a live poller's own query genuinely excludes (e.g. `broadcasts.status='Scheduled'` with a future `scheduled_date` — invisible to both `listActive()` and `listDueScheduled()`), then invoke the runner's processing function directly (`broadcastRunner.processBroadcast(row)`) rather than `.tick()` (which scans and would touch every client's active work on this shared DB, not just yours). Before writing any test that creates a row for ANY background-runner-owned table, check what status/query that runner actually polls for and deliberately avoid it.
- **New reference-content tables** (e.g. `template_library`): seed via an idempotent script under `server/src/db/` (`seedTemplateLibrary.js`'s pattern: upsert by a real unique natural key, never delete-then-reinsert — a client-generated child row like `template_library_usage` would otherwise be orphaned across re-seeds even with `ON DELETE CASCADE`, since a fresh insert gets a new id). Validate content against the SAME real functions the actual submission path uses (`templateParams.js`'s `validateTemplateText`/`validateHeaderText`) before it ever reaches a client, not hand-eyeballed — see `templateLibraryValidation.js`. A migration adding a table a real client will write real rows into should give its `down()` a live-row check before dropping (same pattern as migration `032_widen_forward_events.js`'s down()), not a bare `DROP TABLE`.
- **A test can actively DELETE real shared-table content, not just get raced by a live poller** — a distinct risk from the "live background workers racing test data" entry above (that one is about a live process reading/claiming a test's row; this one is about a TEST'S OWN CODE deleting or truncating rows that were never the test's to touch, via a backup/delete/restore pattern whose restore step can fail). Confirmed for real: `metaTemplateLibraryQA.test.js`'s "empty cache" test (Meta Official Template Library, 2026-08-28) needed to exercise "what does the API return with zero cached rows" against a real (necessarily shared, since `meta_template_library_cache` is server-wide, not per-client) table — its backup-then-delete-then-restore approach is the only viable technique when the assertion needs a DIFFERENT connection (the server's own) to see the delete, which rules out a transaction/rollback pattern (see this file's Known Gaps for the full root-cause writeup: an unstringified jsonb column in the restore step aborted the restore loop after row 1, wiping the real production cache). **The general rule going forward**: any test that must temporarily empty/mutate a real shared (non-tenant-scoped) table to exercise an edge case needs (a) a full backup of every row before mutating, (b) a per-row try/catch on the restore so one bad row can't abort every row after it, and (c) an automatic self-healing fallback (re-run whatever real process would normally repopulate the table, e.g. a refresh runner) if the restore comes up short — not just a bare `try { mutate } finally { restore }` with no failure handling inside the restore itself, which is what let this one slip through.
- **Every migration that adds a column to `messages` must be checked against `routes/metaWebhook.js`'s `enqueueForwards` destructure in `handleInboundMessages`.** That destructure's default behavior is to leak a new column straight into the `message.received` webhook payload sent to every hub/client-webhook/Zapier consumer — it's an opt-out exclusion list (only named fields are dropped), not an opt-in allowlist, so a column silently widens this external wire contract the moment it exists, whether or not that was ever intended. Confirmed real, not theoretical: PLAN.md item 14 added `messages.referral` (2026-09-05) and it leaked as `referral: null` into every ordinary organic message's forward, not just CTWA-sourced ones, caught only because `webhookForwarding.test.js:168` happens to assert the forwarded message's exact key set — a column added before that test existed would have slipped through with zero warning. When adding a `messages` column: either add it to the destructure's exclusion list (if it's internal-only, redundant with another field, or not meant to widen the external contract — the default choice, matching `status`/`direction`/`error_reason`/`meta_error_code`/`referral`'s precedent) or deliberately include it (a scope decision to make and document, not a byproduct of the migration).
- **Test hang troubleshooting — check for stray `node.exe` processes before assuming a code regression.** `server/test/webhookForwarding.test.js` was found (2026-09-05) to intermittently stall for a long, variable time (minutes) in its own setup/teardown, with zero DB activity (`pg_stat_activity` empty), zero established TCP connections, and near-zero CPU during the stall — ruling out a lock, a slow query, or a busy-loop. Root-caused to leftover `node.exe` processes from earlier manual/diagnostic test invocations on the same machine (this session also had long-idle unrelated `chrome-devtools-mcp` node processes adding to the pile) — killing one stray process immediately unblocked a run that had been stuck for minutes and let it complete cleanly. Before re-running a hung suite or suspecting a code regression, run `Get-CimInstance Win32_Process -Filter "Name='node.exe'"` (PowerShell) and kill anything left over from a previous invocation first — a real, demonstrated fix, not a guess. The exact OS-level mechanism (suspected Windows socket/DNS-teardown timing given zero visible activity) was not fully root-caused, but the practical fix is confirmed.

## Update mechanism (how this file stays current)

1. Every build prompt for a new feature ends with an explicit "update CLAUDE.md" instruction, and a build isn't complete without it — same bar as a build without tests.
2. Keep this file, `crm-integration-guide.md`, and the in-app API Guide (`admin/index.html`'s "API Guide" view) in sync but distinct: this file is for Claude Code/internal developers (architecture, conventions, status); the other two are for external developers integrating (endpoints, auth, examples). They overlap in content but serve different readers — don't merge them.
3. Update the feature-inventory table's status honestly, using the three states above — never mark something "Complete + verified" or "Live" without real test evidence.
4. If two sessions touch this file concurrently (this project's local DB is shared, and more than one Claude Code session may be active against the same working tree at once — confirmed to happen in practice), **merge, don't overwrite**: read the currently-committed version first, keep its content intact, and add/update only the rows and sections your own change actually affects.
