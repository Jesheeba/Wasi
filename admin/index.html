API Integration Guide
Hand this to a client's developer to get their CRM sending/receiving WhatsApp messages through Wasi
Go to API Keys
1. Get an API Key

Every client created from the Clients page is auto-issued a Hub API key at creation time — it's shown once in the "Client created" confirmation screen. Lost it, or need a key for a second integration (e.g. Zapier)? Issue one from API Keys, or point the client to Settings → Developer in their own account — clients can self-serve create, revoke, and delete their own keys there.

2. Authentication

Every request needs Authorization: Bearer <api_key>. Keys look like wasi_<48 hex chars>. There is no separate API secret or OAuth flow — the bearer key is the credential.

3. Base URL & Headers

Base URL is this Wasi deployment's own origin. Every write request needs Content-Type: application/json alongside the bearer header.

4. Send a Message — POST /api/v1/messages
curl -X POST https://<wasi-host>/api/v1/messages \
  -H "Authorization: Bearer wasi_..." \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "<CLIENT_UUID>",
    "to": "91XXXXXXXXXX",
    "type": "template",
    "template": "order_shipped",
    "params": { "1": "Priya", "2": "#4821" }
  }'

type: "template" is required outside the 24-hour customer-service window and needs a Meta-approved template. type: "text" with a "body" field only works inside that 24-hour window. client_id in the body must match the key's own client — a defense-in-depth check, not decoration.

5. Manage Templates — GET/POST /api/v1/templates

Same bearer auth. A submitted template must be Meta-approved (minutes to a day) before it can be used in a type: "template" send.

5b. Read Endpoints — Conversations, Contacts, Account, Message Status

Same bearer auth. GET /api/v1/templates/:id (full template definition), GET /api/v1/messages/:id/status (delivery status of a previously sent message, by its Hub-assigned id — not Meta's wamid.*), GET /api/v1/conversations and GET /api/v1/conversations/:id/messages (chat list and history, both accept ?limit=), GET /api/v1/contacts?q= or ?phone= (search), GET /api/v1/account (WABA connection status and quality rating), and GET /api/v1/account/rate-limit (the static rate ceiling below, machine-readable). These were added alongside the Wasi MCP server (see "Connect via MCP / Claude" below) so an AI assistant has read access to the same data a developer's own integration would.

6. Error Handling

Errors come back in one consistent shape across every endpoint: { "error": { "code": "...", "message": "...", ... } } — a stable, machine-readable code to branch on, a human-readable message, and endpoint-specific extra fields nested alongside them (e.g. metaError, Meta's real error body, attached when the rejection happened at Meta, not swallowed; details for validation failures). Check error.code before parsing error.metaError, since not every error originates from Meta (e.g. consent-opt-out rejections, validation errors).

7. Webhooks — Inbound Forwarding

Configure a forwarding URL on the client's Client Detail page (WhatsApp Business Account card → CRM Inbound Forwarding) once their WABA is connected. Deliveries are signed x-wasi-signature-256: sha256=<hmac> — HMAC-SHA256 of the raw JSON body, keyed by a per-client secret. Verify this signature before trusting a delivery. The secret itself is never shown in plaintext after generation — copy it once right after generating/regenerating it on the Client Detail page. Deliveries are queued and retried with backoff, not fire-and-forget.

Event types available: message.received, message_template_status_update, account_update.

8. Rate Limits

The Hub API (/api/v1/*) is capped at 300 requests/minute, currently scoped per source IP (not yet tracked per key). Every response carries live X-RateLimit-Limit / X-RateLimit-Remaining / X-RateLimit-Reset headers so a well-behaved integration can self-throttle before hitting the limit. A rate-limited request gets back 429 with { "error": { "code": "rate_limited", "message": "Too many requests." } }, the same error shape as any other Hub API failure.

9. Security Recommendations
  • Never commit the API key or webhook secret to source control — load them from environment variables.
  • If a key is compromised, delete it from API Keys and issue a new one — deletion takes effect immediately.
  • Always verify the x-wasi-signature-256 header before acting on a forwarded webhook payload.
  • Treat client_id as non-secret (it's a UUID, not a credential) but still avoid logging the API key or webhook secret in application logs.
10. Testing Workflow

Import the Postman collection (link below) with a real key in a local, gitignored Postman environment — never the shared/committed one. Start with GET /api/v1/templates to confirm auth works before attempting a send. Send a type: "text" message to your own test number inside an active 24-hour window before wiring up template sends.

Connect via MCP / Claude — No Integration Code Needed

For a faster path than building a custom integration: Wasi ships an MCP (Model Context Protocol) server that gives Claude (Desktop, Code, or any other MCP-compatible client) direct tool access to send messages, check delivery status, and read templates/conversations — using an existing Hub API key, with zero custom code. This is the same Hub API documented above, wrapped as MCP tools rather than raw REST endpoints.

Hand the client's developer (or a non-technical client who just wants Claude connected) this config, filled in with their own key and this deployment's URL:

{
  "mcpServers": {
    "wasi": {
      "command": "npx",
      "args": ["-y", "@wasi/mcp-server"],
      "env": {
        "WASI_API_KEY": "wasi_...",
        "WASI_API_BASE_URL": "<this Wasi deployment's URL>"
      }
    }
  }
}

Full tool list, example prompts, and troubleshooting are in the server's own README.md (mcp-server/ in this repository). Same security posture as any other API key use: the key lives only in the MCP client's own config, is never logged, and is scoped to exactly this client's data.

Using Claude Code to Build the Integration

If the client's developer uses Claude Code, they can hand it this prompt to scaffold the integration. It's written so Claude implements auth, sends, and webhook verification without ever seeing the raw key.

Before you start: put the API key in an environment variable you set yourself (e.g. WASI_API_KEY in a local .env file, gitignored). Do not paste the raw key into the Claude Code conversation or prompt — Claude only needs the variable's name, never its value. 

I'm integrating my CRM with the Wasi WhatsApp Hub API. Base URL and auth:

- Base URL: <fill in this Wasi deployment's URL>
- Auth: Authorization: Bearer $WASI_API_KEY — read this from an environment
  variable named WASI_API_KEY that I've already set. Never ask me to paste
  the raw key, never print it, never write it to a log or commit it.
- Endpoints: POST /api/v1/messages (send a WhatsApp message — supports
  "template" and "text" types), GET/POST /api/v1/templates (list/submit
  templates).
- Every request needs client_id (my Wasi client UUID, not secret) matching
  the key's own client.
- Errors come back as { error, code, metaError? } — handle both a plain
  `error` and a Meta-originated `metaError` distinctly.
- I also receive inbound webhooks signed with header
  x-wasi-signature-256: sha256=. Verify
  this signature before trusting a payload, using a constant-time compare.

Please implement: (1) a small client module wrapping authenticated calls to
these two endpoints with typed request/response handling, (2) an inbound
webhook receiver that verifies the signature and dispatches on event type,
(3) error handling that surfaces `metaError` distinctly from a plain
validation error, and (4) a way to test all of this against real values
without printing WASI_API_KEY or WASI_WEBHOOK_SECRET anywhere.
